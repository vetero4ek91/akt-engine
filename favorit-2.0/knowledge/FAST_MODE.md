# Быстрый режим осмотров: фото → перечень → PDF

Введён 19.11.2026 после замеров: штатный JS 0,34–0,42 с; конвертация LibreOffice 2,73–2,98 с; технический сборщик с проверками 3,31 с на тестовой Калине, 4 страницы. Это измеренное время **только сборки**, не анализа фото и не всей беседы.

## Выводы из серии измерений и нового чата

- На новой машине полный пользовательский замер иногда составлял 123–225 секунд; повторные сборки подготовленного акта занимали 59–62 секунды. Это наблюдения отдельных тестов, а не измерение серверных стадий.
- Длинный контекст, изображения в PDF, последовательные обращения к инструментам и передача результата **возможные** источники задержки; ни один не доказан единственной причиной. Новый чат — **эксперимент**, а не гарантированное ускорение.
- Сокращать количество последовательных вызовов; независимые запросы GitHub объединять. Не выполнять повторный просмотр и рендер тех же страниц, если они уже видны и читаемы.
- Измерять инструментальные стадии при сборке, а весь цикл — по пользовательскому секундомеру; время появления ответа в мобильном приложении из облачного Python недоступно.
- Для нового чата читать [короткий протокол](NEW_CHAT_START.md). Он не отменяет обязательной проверки `PROMPT.md` и актуального `Favorit_AKT_autonomous.js`.
- До выдачи акта: одна сборка, автоматическая проверка и один визуальный обзор. После выдачи при необходимости отдельно разбирать ошибки и обновлять базу.

## Приоритет: скорость без домысливания

1. **Фотографии по умолчанию являются основным вводом.** Не требовать диктовку. Прочитать один раз все имеющиеся страницы пакета и направление; если изображения уже предоставлены как просмотр страниц PDF, не делать повторный рендер и не запускать OCR без реальной причины.
2. **Один проход по зонам.** На первом проходе идентификация и сторона (по ходу движения, два независимых ориентира), на втором — видимые повреждения с привязкой к фото, на третьем — только короткий чек-лист часто пропускаемых деталей (скрытое НЕ приписывать).
3. **Сразу готовить структурированный результат**, не писать промежуточные длинные отчёты. Формат: список из пронумерованных деталей, короткие технические описания; отдельно подтверждённые эксплуатационные дефекты. Неизвестные данные — пустыми или с пометкой; не выдумывать.
4. **Собирать сразу после команды «собирай»**, не запрашивать повторное подтверждение. Если пользователь заранее разрешил сразу акт, пропустить этап переписки со списком, но внутренний структурированный перечень обязателен.
5. **Никакого многократного пересоздания с нуля**: использовать текущие `favorit-2.0/PROMPT.md` и `Favorit_AKT_autonomous.js` из GitHub `main`; менять только блок `const D`/входных данных в рабочей копии. Бланк от 18.11.2026, факсимиле и разметка подписи уже внутри JS; отдельных файлов не требуется. Оригинал не переписывать. Для ЛАТ применять отдельный прежний бланк и генератор.
6. Для Фаворита использовать `favorit-2.0/tools/fast_build.py` с `--generator` (автономный JS с заполненным блоком данных), чтобы сделать DOCX → PDF и автоматически проверить номер убытка на всех страницах, VIN в физической сетке, начало повреждений с листа 3, наличие названий позиций и встроенных изображений факсимиле. **Это не заменяет визуальную проверку** галочек, подписей, обрезки, переносов и смысла.
7. **Визуальная проверка в один цикл**: рендер страниц низкого разрешения для обзорной сетки, затем увеличить только проблемные места. Если техническая/визуальная проверка не пройдена, PDF пользователю не выдавать.
8. Измерять отдельно: время получения фото → готовый перечень; время заполнения входных данных; время сборки и проверки PDF. Не обещать 10/30 секунд на весь осмотр на основании теста самого генератора.
9. После проверки пользователем сохранять не стенограмму, а **краткую карточку ошибки** в `CORRECTIONS.md`: что пропустили/перепутали, как эксперт исправил, что проверять в следующий раз. Не трогать рабочий генератор ради учебного исправления.

## Минимальный чек-лист фотоанализа

- Передний удар: бампер, кронштейны, накладки, фары и **крепления** фар, ПТФ, крыло, капот, панель передка, лонжерон, подкрылок, защита двигателя.
- Задний удар: основная облицовка, нижняя накладка, отражатели **слева и справа**, кронштейны, две лампы номера, госномер, дверь задка, крылья; различать нарушение зазора и собственное повреждение детали.
- **ДТП и старый дефект могут быть на одной детали**: отдельные описания, например свежий залом лонжерона и давняя сквозная коррозия.
- Крупный план с пальцем или линейкой — сигнал проверить названную деталь и размер, но не доказательство скрытого разрушения.

## Пример запуска быстрого сборщика

```sh
python favorit-2.0/tools/fast_build.py \
  --generator /tmp/current-act/Favorit_AKT_autonomous.js \
  --core-fnv КОНТРОЛЬНОЕ_ЧИСЛО_АКТУАЛЬНОГО_JS \
  --output /tmp/current-act/final.pdf \
  --claim 0020969178 \
  --vin XTA11193080052435 \
  --damage "Бампер передний" \
  --damage "Крыло переднее правое"
```

Путь `--generator` указывает на рабочую копию **актуального автономного JS** с заполненным блоком данных. Остальные исходники не нужны. `--core-fnv` — контрольное число суффикса JS, рассчитанное по текущей версии из GitHub; это не текстовый литерал: подставить фактическое число. Скрипт не изменяет входной JS. Для анализа/сверки использовать все фактически заявленные позиции в опциях `--damage`, а не только две из примера. Зависимости в облачной среде: Node.js, `zip`, `unzip`, LibreOffice, Python 3, PyMuPDF (`fitz`).

**Статус:** успешная пробная сборка автономного JS на LADA XRAY с 22 позициями и 5 листами не заменяет проверку реального акта с полными реквизитами. `AKT_TEST=1` только для явно помеченных тестов.
