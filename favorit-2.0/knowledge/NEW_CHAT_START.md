# Запуск нового чата: Фаворит 2.0, зимний быстрый режим

Дата: 19.11.2026. **Назначение:** стартовая краткая инструкция для нового чата, чтобы не перечитывать прежний длинный диалог.

## Приоритеты
1. **Точность и скорость:** целевой пользовательский замер — не более **90 секунд от отправки полного комплекта до появления PDF**. Не гарантировать это время заранее.
2. **Работай по доступным исходникам:** готовый перечень, диктовка или фото. При наличии перечня или диктовки не требуй фото. По прямой команде собирай без повторных согласований. Уточняй только конкретный факт, без которого нельзя закончить задачу.
3. **Один проход по исходникам:** для больших фото-PDF сначала построить индекс кадров `tools/photo_contact_sheet.py` (без OCR, 25 страниц Vesta: тест 1,55 с), проверить по общим видам сторону автомобиля и открыть крупно только нужные кадры. Затем реквизиты и фото → два независимых списка «ДТП» и «эксплуатационные» → заполненный блок входных данных → генерация → машинный контроль и **один** визуальный обзор → PDF. С внутренним отчётом экспертной проверки по правилам `PROMPT.md`, без повторного OCR всех страниц, лишних монтажных изображений, множества конвертаций и обновления базы до выдачи результата.
4. **Не угадывать:** тип страхования, номер убытка, ремонтные воздействия, VIN, сторону, подписи, состояние «на ходу», принадлежность старых дефектов. Если факт не установлен — оставить неизвестным или отметить ограничение. Тестовый PDF не выдавать за действующий.
5. **Стороны по ходу движения**. При выводе по фотографиям используй два независимых ориентира. Готовый список или диктовку сверяй с имеющимися данными. Сопряжённые элементы и внутренние части проверить по имеющимся фото; не объявлять скрытые повреждения установленными. Особенно проверять: фары и крепления, подкрылки, спойлеры/накладки, два отражателя/фонаря номера, нижние/силовые детали. Дефекты эксплуатации искать отдельным обходом всех 4 сторон.
6. **Перед сборкой ассистент сам сверяет** `favorit-2.0/PROMPT.md` и `favorit-2.0/Favorit_AKT_autonomous.js` с **GitHub main**. Если исходный JS уже прикреплён к проекту, получить GitHub blob SHA через короткий запрос к файлу и сравнить с `git hash-object` исходного локального JS. При совпадении не скачивать большой встроенный бланк повторно; прочитать проверенный локальный файл. При несовпадении получить актуальную версию самостоятельно. Пользователю сообщать только о реальной блокировке доступа. Для разбора повреждений без PDF проверка движка не требуется. Справочник и короткие правила читать одним параллельным запросом. Использовать автономный JS: новый бланк, подпись и XML-разметка уже внутри него; отдельные DOCX/PNG/TXT/`podpis.js` не нужны. Не менять рабочий генератор: только входной блок `const D` и сопровождающие переменные до отметки «Конец блока данных». Не проводить самостоятельный рефакторинг во время осмотра.
7. **Страховые не смешивать:** для Фаворита бланк от 18.11.2026, для ЛАТ АССИСТАНС прежний отдельный бланк. Общая экспертная методика подходит всем, правила формы различаются.
8. **Контроль PDF:** подготовить независимый согласованный список деталей `approved_damages.txt`; передать в `tools/fast_build.py` как `--approved-damages` вместе с `--generator`, `--core-fnv` и обязательным `--expert-review` (формат в `FAST_MODE.md`). Скрипт проверяет все названия и описания, количество и нумерацию повреждений, VIN, номер убытка, основные галочки, факсимиле и начало перечня с листа 3. После этого один визуальный просмотр PDF. Для КАСКО ремонтные воздействия только при обосновании. Если ошибка — исправить и только потом выдавать. Тест с неполными данными под `AKT_TEST=1` не считать готовым реальным актом.
9. **Никаких GitHub-коммитов в горячем пути сборки.** Если `CHECKS.dismantling=true`, текущий автономный генератор не поддерживает такую отметку, сборщик блокирует акт. При необходимости сообщить конкретную причину, не выдавать неверный PDF. При сравнении с контрольным актом в другой задаче записывать исправления в `knowledge/CORRECTIONS.md`. Во время срочного акта только читать, строить и отдавать.
10. **Скорость:** времена Node/LibreOffice 3–6 секунд измеряли, но это не весь цикл. Реальные пользовательские замеры из предыдущего чата: повторные Vesta 59 секунд, Granta 62 секунды; новый Lifan 123 секунды, новая Granta 225 секунд. Эти цифры нельзя обобщать как гарантированную производительность. Время старта сообщения и доставки ответа обычно недоступно модели; пользователь измеряет на клиенте. По возможности замерять этапы инструментально, без удлинения процесса лишними вызовами.

## Ссылки по необходимости
- `favorit-2.0/PROMPT.md` — обязательные правила бланка.
- `favorit-2.0/Favorit_AKT_autonomous.js` — **основной актуальный генератор Фаворита** (один JS со встроенным бланком и факсимиле).
- `favorit-2.0/New_Favorit_AKT_refined.js` — резервный предыдущий генератор, использовать лишь при явно согласованном откате.
- `favorit-2.0/EXPERT_KNOWLEDGE.md` — экспертная методика.
- `favorit-2.0/knowledge/CORRECTIONS.md` — уроки прошлых ошибок.
- `favorit-2.0/knowledge/FAST_MODE.md` — технический быстрый маршрут.
- `favorit-2.0/tools/fast_build.py` — единый сборщик с машинным контролем.
- `favorit-2.0/tools/photo_contact_sheet.py` — быстрые обзорные листы фотоальбома для одноразового просмотра.

**Принцип:** пользователь получает проверенный PDF раньше объяснений об устройстве системы. Не путать скорость генератора со скоростью ответа.
